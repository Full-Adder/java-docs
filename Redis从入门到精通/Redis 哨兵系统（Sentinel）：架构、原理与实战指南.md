# Redis 哨兵系统（Sentinel）：架构、原理与实战指南

## 介绍
Redis 哨兵系统是 Redis 的高可用性解决方案，用于监控 Redis 主服务器的运行状态，自动进行故障转移，并在主服务器下线时将从服务器提升为新的主服务器。本文将深入探讨 Redis 哨兵的架构和原理，并提供实战指南，帮助读者在实际项目中部署和使用 Redis 哨兵系统。

## Redis 哨兵系统概述

Redis 哨兵系统由一个或多个哨兵实例组成，它们共同协作，完成以下任务：

- **监控**：监控主服务器和从服务器的运行状态。
- **通知**：当检测到故障时，哨兵之间会相互通知。
- **自动故障转移**：在主服务器下线时，自动将一个从服务器提升为新的主服务器。
- **配置传播**：将新主服务器的信息通知给其他哨兵和从服务器。

## Redis 哨兵架构原理

### 监控机制
哨兵系统通过定期发送 PING 命令来检测 Redis 服务器是否在线。

### 故障转移
当哨兵检测到主服务器下线时，会进行以下步骤的故障转移：

1. **主观下线**：单个哨兵发现主服务器下线，称为主观下线。
2. **客观下线**：当足够多的哨兵同意主服务器已下线时，称为客观下线。
3. **选举领导者**：哨兵之间会进行领导者选举，选出一个哨兵来执行故障转移。
4. **选择新的主服务器**：领导者选择一个从服务器，将其提升为新的主服务器。
5. **更新配置**：领导者将新主服务器的信息更新到其他哨兵和从服务器。

### 数据迁移
新的主服务器会开始接收写入请求，而其他从服务器会开始复制新的主服务器的数据。

## Redis 哨兵实战指南

### 环境准备
假设我们有三台服务器，一台作为主服务器，两台作为从服务器，另外两台作为哨兵服务器。

### 安装 Redis
在所有服务器上安装 Redis。

### 配置 Redis 主从复制
参考前面一节完成主从复制搭建

### 配置哨兵
在三台哨兵服务器上修改 `sentinel.conf` 文件，配置哨兵的监听端口和监控的主服务器信息。

```bash
port 26379
sentinel monitor mymaster 192.168.64.66 6379 2
```

这里的 `mymaster` 是主服务器的别名，方便哨兵    系统引用。

### 启动哨兵
使用 `redis-sentinel` 命令启动哨兵。

```bash
redis-sentinel sentinel.conf
```

### 验证哨兵系统
使用 `redis-cli` 连接到哨兵，查看哨兵状态。

```bash
redis-cli -p 26379 info server

SENTINEL master mymaster
```

### 测试故障转移
为了测试故障转移，可以停止主服务器的 Redis 服务，并观察哨兵系统是否自动执行故障转移。

```bash
redis-cli -p 6379 shutdown
```


## Redis 哨兵系统优缺点

### 优点
- **高可用性**：自动故障转移机制提高了系统的可用性。
- **数据保护**：哨兵系统可以防止数据丢失。
- **易于部署**：哨兵系统相对容易部署和管理。

###  缺点
- **复杂性**：增加了系统的复杂性。
- **性能开销**：哨兵系统会占用一定的系统资源。
- **数据一致性**：在故障转移期间，可能会出现短暂的数据不一致。

## Sentinel日志详解
### Sentinel 启动日志

当 Sentinel 启动时，会记录相关的配置信息和启动状态：

```log
1234:X 08 Jun 2024 10:00:00.000 # Sentinel ID is 1234567890abcdef
1234:X 08 Jun 2024 10:00:00.001 # +monitor master mymaster 127.0.0.1 6379 quorum 2
```

- `Sentinel ID`：表示 Sentinel 实例的唯一标识。
- `+monitor`：表示 Sentinel 开始监控指定的主节点 `mymaster`，其 IP 地址和端口为 `127.0.0.1:6379`，选举时至少需要 `2` 个 Sentinel 同意故障转移。

### 检测主观下线

当 Sentinel 发现主节点无响应时，会将其标记为主观下线（Subjectively Down，简称 SDOWN）：

```log
1234:X 08 Jun 2024 10:05:00.000 # +sdown master mymaster 127.0.0.1 6379
```

- `+sdown`：表示 Sentinel 认为主节点 `mymaster` 处于下线状态。

### 检测客观下线

如果多个 Sentinel 一致认为主节点下线，则标记为客观下线（Objectively Down，简称 ODOWN）：

```log
1234:X 08 Jun 2024 10:05:05.000 # +odown master mymaster 127.0.0.1 6379 #quorum 2/2
1234:X 08 Jun 2024 10:05:05.001 # +new-epoch 1
1234:X 08 Jun 2024 10:05:05.002 # +try-failover master mymaster 127.0.0.1 6379
```

- `+odown`：表示主节点 `mymaster` 被标记为客观下线，`quorum 2/2` 表示 2 个 Sentinel 同意该判断。
- `+new-epoch`：表示故障转移的一个新周期开始。
- `+try-failover`：表示开始尝试故障转移。

### 选举新主节点

在故障转移过程中，Sentinel 会选举一个从节点作为新的主节点：

```log
1234:X 08 Jun 2024 10:05:10.000 # +vote-for-leader 1234567890abcdef 1
1234:X 08 Jun 2024 10:05:10.001 # +elected-leader master mymaster 127.0.0.1 6379
1234:X 08 Jun 2024 10:05:10.002 # +failover-state-select-slave master mymaster 127.0.0.1 6379
1234:X 08 Jun 2024 10:05:15.000 # +selected-slave slave 127.0.0.1:6380 127.0.0.1 6380 @ mymaster 127.0.0.1 6379
1234:X 08 Jun 2024 10:05:15.001 # +failover-state-send-slaveof-noone master mymaster 127.0.0.1 6379
```

- `+vote-for-leader`：表示 Sentinel 投票选举某个从节点为新主节点。
- `+elected-leader`：表示某个 Sentinel 被选为领导者，负责此次故障转移。
- `+selected-slave`：表示选中的从节点，其地址为 `127.0.0.1:6380`。
- `+failover-state-send-slaveof-noone`：表示向选中的从节点发送 `SLAVEOF NO ONE` 命令，使其成为主节点。

### 故障转移完成

故障转移完成后，新的主节点将被确认并通知其他节点：

```log
1234:X 08 Jun 2024 10:05:20.000 # +failover-end master mymaster 127.0.0.1 6379
1234:X 08 Jun 2024 10:05:20.001 # +switch-master mymaster 127.0.0.1 6379 127.0.0.1 6380
1234:X 08 Jun 2024 10:05:20.002 * +slave slave 127.0.0.1:6379 127.0.0.1 6379 @ mymaster 127.0.0.1 6380
1234:X 08 Jun 2024 10:05:25.000 * +slave slave 127.0.0.1:6381 127.0.0.1 6381 @ mymaster 127.0.0.1 6380
```

- `+failover-end`：表示故障转移过程结束。
- `+switch-master`：表示主节点切换完成，新的主节点地址为 `127.0.0.1:6380`。
- `+slave`：表示原主节点和其他从节点开始作为新主节点的从节点进行同步。

## 总结

Redis 哨兵系统是实现 Redis 高可用性的关键技术。通过本文的介绍，读者应该对 Redis 哨兵的架构和原理有了深入的理解，并掌握了如何在实际项目中部署和使用 Redis 哨兵系统。在生产环境中，建议结合实际业务需求，合理配置哨兵系统，以确保系统的稳定性和可用性。同时，也可以考虑使用 Redis Cluster，以实现更高级的分布式特性。
